# Postgres capacity and precision

Audit baseline: the migrated PostgreSQL 17 schema through the performance metric precision fix and the server and worker SQL that reads or writes it. The figures below are capacity scenarios. They are independent of production traffic or benchmark results.

## Five-year envelope

Five years at 365.25 days per year is 157.8 million seconds. A lifetime counter crosses signed int32 at 13.6 units per second, or 1.18 million per day. At 100 pages/s, a corpus grows by 15.8 billion pages. At 1,000 search or usage events/s, a counter grows by 158 billion events. With 1,000 tokens/page at 100 pages/s, usage grows by 15.8 trillion tokens. A run can cross int32 independently of time: 107,375 documents at 20,000 pages each exceed it. Project-wide jobs take their totals from existing corpora, so intake request limits do not bound a run's totals.

| Path | Decision and evidence |
| --- | --- |
| Run totals | Widen document, processed document, page and processed page counts together. Checkpoint SQL also uses bigint for the page delta. The unchecked page accumulator normally resets after 25 pages or 10 credits. Both triggers are configurable and can be disabled, so the accumulator can span a run. |
| Extract settlement | Widen the settled page total of its run. Keep the page × artifact-bytes estimate and the source-byte addition integral in SQL. |
| Usage ledger | Widen whole input/output token counts. A run-level rollup can exceed int32 using ordinary receipts, and embedding can also emit a multi-batch token receipt. Widen `amount` from `numeric(12,4)`, whose maximum is 99,999,999.9999, to exact numeric. A storage quantity expressed in GiB previously lost all sub-0.0001 GiB detail. The migration continues to reject infinite values and preserves existing values, including any previously rounded values. |
| Attribution and costs | The view continues to multiply exact numeric amounts, costs and tokens by its numeric split share. Budget checks, settlement and debit SQL retain the existing `numeric(24,12)` money fields and calculations. Usage reporting sums decimal JSON cost estimates in SQL before projecting its existing numeric result. |
| Graph jobs | Rebuilds add token and cost increments across a project. Widen token totals and align accumulated cost with `numeric(24,12)` used by usage events. A 4-decimal accumulator rounded each write to 0.0001 cents; an increment of 0.000049 cents rounded to zero on every checkpoint. |
| Project and search readers | Keep lifetime usage, corpus and activity counts, search coverage, and token and character sums wide through aggregation. A byte-exact or fractional quantity stays exact through SQL arithmetic. The run forensics query sums chunks and counts pages independently so multiple pages cannot multiply a document's token count. |
| API key usage | The active minute buckets are distinct from retired subscription/rate tables. A daily use total can exceed int32 even when each bucket fits. The daily check compares already booked usage to an int32 quota and may observe concurrent completions. Keep wider totals in quota checks and key listings. |
| Mastra | The pinned adapter defines `totalTokensObserved` as int32, and its memory adapter reads it through `Number`. It takes only 21,475 observations of 100,000 tokens to exceed int32. DocSlurp uses bounded message history and does not enable Observational Memory. Revisit the provider schema and arithmetic upstream before enabling it. [Mastra Observational Memory](https://mastra.ai/docs/memory/observational-memory) |

Page, chunk and asset ordinals, dimensions, HTTP statuses, retry counters and per-document durations remain narrow. For example, recorded page-extract durations have an explicit one-day check, and the default upload byte limit is 500 MiB with a smaller buffered multipart limit. Shard counters and minute buckets cover bounded scopes. The minute page bucket crosses int32 only above 35.8 million pages/s for one key. Real-valued confidence, plausibility, quantization and ratios are approximate scores, and their precision requirement is independent of service age. Corpus/activity counters and backfill token storage already use bigint. The prior performance telemetry fix already uses unconstrained numeric. Retired tables are outside the upgrade.

## Application and release boundaries

The public API and workflow payloads still use JavaScript numbers. PostgreSQL bigint arrives as text in the raw client. Run readers convert it explicitly, and some SQL projections emit a double only after exact aggregation. Exact integer representation in these payloads ends at `Number.MAX_SAFE_INTEGER` (9,007,199,254,740,991). Crossing it on a five-year counter takes about 57 million units/s sustained. At 1,000 tokens/page that is about 57,000 pages/s in the same scope. Byte totals hit it at about 57 MB/s sustained with no retention or deletion. Byte totals are already number-valued, so callers that need byte-exact data above 8 PiB require a separately versioned representation. SQL storage preserves the full bigint range. Monetary display numbers are approximate, and debit and cap SQL use decimals. [PostgreSQL numeric types](https://www.postgresql.org/docs/17/datatype-numeric.html)

1. Release the compatible readers to the API and workers while the old schema is still installed. Confirm that old binaries have drained. A migrator that runs before application rollout needs this step in a separate release. The reader release is also the rollback target after the schema changes.
2. Check relation and index sizes and disk/WAL headroom in the target environment. Rehearse the four rewrites on a representative restored database before scheduling them. Each UTC migration uses a separate transaction and the migrator's lock timeout. The timeout limits lock acquisition. The locks remain held while PostgreSQL rewrites the table and rebuilds its indexes. [PostgreSQL ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html)
3. The usage migration preserves the view identity, output types, definition, options and ACL. The run migration recreates the corpus trigger and rebuilds the shipped `admin_stats` materialized view, including its previous populated state, public column types and effective relation grants. A customized owner, column grant, index, settings or comments fail the migration explicitly. A dependent object blocks the non-cascading drop. The refresh takes a second pass over run rows when the view was populated.

Production rewrite time requires relation sizes and a populated rehearsal. Empty local migration times estimate neither production duration nor impact.
