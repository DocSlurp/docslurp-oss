# Integrity candidate adjudication

The integrity judge accepts an optional trusted operator-supplied JSON attestation.
It never changes detection, deletes comments, or waives findings. Without a record,
candidates retain `needs-review`. Any invalid or rejected record blocks promotion.

API: `judgeIntegrity({ dataset, repo?, base?, reviewContext?, adjudication? })`.
`adjudication` is a JSON file path, not a boolean or an object. Unknown API keys
and unknown/duplicate CLI options are rejected. CLI equivalents are `--dataset`,
`--repo`, `--base`, `--review-context`, `--adjudication`; `--output` saves the report.

First scan with a fresh operator-assigned review context. Give an independent
reviewer the scan and source context. Supply their explicit decisions in an
external file; do not place review records in production source. No acceptance
record is generated by the tool.

The exact record keys are:

- `schema`: `docslurp-integrity-adjudication@v1`.
- `datasetHash`, `productionHash`, `candidateSetHash`, `reviewContext`: exact scan bindings.
- `reviewer`: exactly `identity` (nonempty string), `independent` (true), and
  `provenance` (nonempty string identifying the independent session/person and basis
  for independence from authorship).
- `decisions`: exactly one entry per candidate, with exactly `candidate` (the entire
  candidate object from the report), `decision` (`accept` or `reject`), `reason`
  (nonempty string), and `reviewedAt` (UTC ISO timestamp with milliseconds, not future).

Candidate bindings include rule, file, origin, line, evidence hash and occurrence
ID. The set hash binds the ordered complete set, including repeated occurrences.
Missing, extra, duplicate, changed or rejected decisions fail closed. Dataset,
source, repository revision, index, or candidate changes invalidate applicable
bindings. Findings always block, even alongside a valid accepted record.

## Trust boundary and limitations

Operators must validate reviewer identity, independence, provenance and rationale
out of band. The schema checks their presence, not their truth. Hashes provide
content binding, not cryptographic identity, signatures or autonomous proof.
An attacker who controls the attestation can assert a false review. Restrict access
to records and to the operator's invocation. Two council reviews of this mechanism
are a separate prerequisite, not supplied by an attestation about candidates.

Use a fresh review context for each new review. Cross-context replay fails;
identical records are intentionally reusable for idempotent verification of the
same context and exact scan. There is no consumed-token store, expiration policy,
or automatic proof of reviewer independence. Do not reuse contexts for new reviews.

Never copy expected-answer plaintext into rationale or provenance. Reports retain
only the record hash and acceptance status, not reviewer free text. Retain the
external record securely for audit. No real held-out run or acceptance is part of
this implementation's synthetic validation.
