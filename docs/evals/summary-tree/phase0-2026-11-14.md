# Summary tree, phase 0: quality and reuse (2026-11-14)

Development-set evidence for the summary-tree plan's phase 0. It covers the
"Quality" and "Reuse" parts. The production latency experiment is not part of
this run, so nothing here says whether the tree leg fits a deadline.

**Status: no go/no-go decision.** The kill rule is not applied: the
development set has 11 cases per question class (one case is 9.1 points, the
rule's thresholds are 2 and 3 points), the `guide` and `include` legs are a
harness simulation because the retrieval leg does not exist, and the sealed
confirmation set has not been run. What the data does show is under
[Findings](#findings).

The tree was built twice on the same corpus, chunks and vectors:

- **Product library**: the summary-tree library from the feature branch
  (commit `c4fcc9166`, not yet on `main`), loaded at run time: its leaf
  selection, grouping, hashing, prompt, parser and truncation rule at its
  default limits (4 to 16 leaves per group, fan-in 3 to 10, about 150 words).
- **Stand-in**: `scripts/summary-tree-eval/grouping-standin.mts`, written
  before the library landed, at 3 to 8 leaves per group, fan-in 2 to 8, about
  120 words. Kept as a second configuration.

## Corpus and cases

Eleven public documents, 2,304 pages, 7,086 chunks (6,281 summarizable
leaves), listed with URL, licence and hashes in `sources-manifest.json`.
Source bytes are outside the repository. Text is paged with the product text
page rule so page citations can be scored; chunking, contextual preambles and
embeddings are the product's own code at default pipeline settings.

| Slice | Documents | Pages |
| --- | --- | ---: |
| Headed (5) | two long non-fiction books, one essay collection, two protocol specifications converted from HTML | 1,090 |
| Heading-less (6) | five plain-text books with no `#` heading at all, and one HTML book whose chapter titles are not headings (5 headings in 262 pages) | 1,214 |

Cases (`development-cases.json`, built and verified by `cases.mts`): 33
development cases, 11 each of fact lookup, multi-section (two premises in
different places) and whole-document (two or three premises spread across the
document); 15 on headed documents and 18 on heading-less ones. Every gold
quote is verbatim, on one page, and inside one chunk. The confirmation set (22
cases: 11 fact, 9 multi-section, 2 whole-document) is sealed outside the
repository; `confirmation-manifest.json` holds its hash. **It is too thin on
whole-document questions (2) and needs about nine more before it can gate.**

## Scorers

No scorer was written for this eval.

- Retrieval: `scripts/retrieval-quality/eval.mjs` `score`, k = 10.
  Components: **support@10** (every premise's quote, document and page in one
  result), **premise coverage** (share of premises found), **reciprocal rank**
  (joint), **primary page**.
- Answer: the `answer` check of `scripts/multisearch-quality/score.mjs`
  `scoreCase` (required patterns in the reader's answer). The reader is the
  default text model with the top-10 results as context.
- `tree-include` returns summaries, which cannot contain a gold quote. Its
  strict components score only its seven chunks; the **mapped** components
  count a summary as the chunks under it.
- **Composite**: mean of support@10, premise coverage, reciprocal rank and
  answer check (mapped retrieval components for `tree-include`). Read the
  components first.

**The answer check is diagnostic only.** The closed-book reader passes 100% of
fact cases and 72.7% of multi-section cases with no context, because the
sources are famous texts. It also demands the source's own wording, which
fails correct paraphrases on whole-document questions. Retrieval components
are the evidence; long context can only be compared on the answer check.

## Findings

1. **Project defaults cost more than any arm gains.** `dedupeByFilename`
   defaults to on and keeps one result per document whenever results span two
   or more documents. On this 11-document project it takes support@10 from
   51.5 to 36.4 over all cases and from 27.3 to 13.6 on broad ones. A question
   about one long document in a multi-document project gets at most one chunk
   from it. Every other arm here runs with it off. The tree cannot help while
   this default stands.
2. **Zero-build arms do not move retrieval.** `summarySeed` changed premise
   coverage by 1.5 points on broad questions and support@10 by nothing: it
   narrows to the top five documents, and these questions already retrieve
   from the right one. Document order is the same ten results by
   construction; only its rank component moves (down).
3. **Whole-document questions fail on retrieval today**: 0 of 11 with joint
   support in every zero-build arm. This is the gap the tree is for.
4. **The simulated `guide` leg helps broad questions on the product-library
   tree**: support@10 27.3 to 40.9 (three more of 22 cases), premise coverage
   49.2 to 61.4 against the best zero-build arm, composite 32.9 to 38.6. The
   gain is larger on heading-less documents (support 16.7 to 33.3) than on
   headed ones (40.0 to 50.0). On the stand-in tree, with groups half the
   size, coverage rose (57.6) but joint support did not (27.3).
5. **`include` trades chunk slots for coverage that strict scoring cannot
   see**: strict support@10 31.8, mapped 50.0; mapped premise coverage 75.8.
   Whether a summary is acceptable evidence is a product question this
   scorer cannot answer.
6. **The fusion rule lost fact lookups.** `guide` lost 1 of 11 fact cases and
   `include` 2 of 11 on the product-library tree. In the lost `guide` case
   the supporting chunk was rank 2 in the chunk leg; all ten returned chunks
   appeared in both lists and outranked it under plain reciprocal rank fusion
   (trace in the raw outputs). The retrieval leg needs a rule that cannot
   displace the chunk leg's top results. On the stand-in tree no fact case
   was lost.
7. **Long context beat every retrieval arm on the answer check** for broad
   questions (68.2 against 40.9 to 45.5), on documents of 72,000 to 310,000
   tokens that all fit the default model. It read 170,500 tokens per question
   on average against about 3,400 for a retrieval arm; median reader latency
   was 3.4 s (maximum 49 s) against 1.2 s. At list prices, one long-context
   question costs about as much as half of one document's tree build, so long
   context is cheaper only up to about two questions per document. The
   comparison rests on the weak answer check.
8. **One provider refusal in about 3,400 summary calls, and one in about 460
   reader calls.** The default text model's only host refused output for a
   passage of a 19th-century novel ("output data may contain inappropriate
   content"). The summary call succeeded on a later attempt. Under the plan,
   a group that keeps failing leaves the document `partial` and unserved, so
   the stage needs a defined path for content refusals.
9. **Group shape.** Under "a short section is one group", 340 of the
   product library's 1,067 leaf groups hold a single chunk (198 of them in
   one specification with 311 headings), each paying a model call to restate
   one chunk. Deep heading nesting gives tall, thin tops: a 68-page
   specification got a nine-level tree whose levels 5 to 9 hold one node
   each, five near-whole-document summaries.

leaf vectors, a proxy for summary vectors. "Different extractor" compares the

Stand-in (same pairs): identical 100%; paragraph inserted 94.7 to 96.7% node
reuse; heading renamed 92.6 to 95.9%; EPUB 91.8%; plain text 0%. Rows in
`results/reuse-2026-11-14.json`.

What it shows:

- Identical bytes reuse everything; a retry makes no call.
- One inserted paragraph or one renamed heading keeps 90 to 95% of nodes in
  headed documents: the edited group and its path to the root. A thin top
  makes that path long (five of seven new calls in the specification).
- **In the heading-less book one inserted paragraph changed 5 of 28 leaf
  groups** and kept 73.5% of nodes, although 99.6% of leaves were unchanged.
  Leaf vectors include the contextual preamble, which carries page numbers;
  the insertion shifts later pages, so untouched chunks get new vectors and
  the lowest-similarity cuts move. Cutting on vectors that do not depend on
  the page would remove this.
- A different extractor that changes headings or paragraphing reuses nothing
  (0% of nodes with 35 to 51% of leaves intact). The same converter over a
  different container reuses about 90%.

Against the plan's estimates: build cost is just below the estimated range
(12,000 to 23,000 pages per $1), speed is a third to a half of the estimate
(105 to 170 pages per minute per call), and storage is 1.5 to 3 times the
estimate (1.2 to 2.4 GB per 1M pages). Measured chunk density was 3.1 chunks
per page (2.7 leaves per page), the assumption the plan flagged as
unconfirmed.

## Kill rule

| Rule | Development reading (product-library tree) | Applies? |
| --- | --- | --- |
| Broad questions gain under 3 points over the best zero-build arm | `guide`: support@10 +13.6, premise coverage +12.2, reciprocal rank +1.9, answer check −4.6, composite +5.7. `include`: mapped support +22.7, composite +13.0. On the stand-in tree: support +0, coverage +8.4, composite +0.4 | Not decidable |
| Fact lookups lose more than 2 | `guide` −9.1 support@10 (one case), `include` −18.2 (two cases); 0 on the stand-in tree. Cause is the fusion rule (finding 6) | Not decidable |
| Long context matches the tree at lower cost for documents that fit | Long context is ahead on the answer check and cheaper only below about two questions per document | Not decidable |

Not applied, for four reasons: 11 cases per class cannot resolve 2 or 3
points; the tree legs are simulated with a fusion rule nobody has designed
yet; the only component shared with long context is contaminated by the
reader's prior knowledge; and this is the development set. The rule's
thresholds need a few hundred cases per class to be meaningful.

## Integrity gate

`scripts/evaluation-integrity-judge.mjs` over all 55 cases (development and
sealed), `--base origin/main`:

- First run: **failed**, 2 findings. The reuse script carried a default list
  of source identifiers. The list moved to the manifest (`reuseBase`), and the
  reuse experiment was run again from the clean code.
- Second run: **passed**, 0 findings, 0 candidates.
- Final run on the tree this report is committed with: **passed**, 0
  findings, 0 candidates, 55 cases, 1,737 production files scanned.

No tuning step read the sealed file. Results labelled "v1" in the raw output
directory used a chunk leg fetched only at depth 50, which reorders the top
ten by itself; they are kept, not reported, and the reported "v2" keeps the
product's own top ten first.

## Blocked, and on what

1. **Confirmation run**: on the retrieval leg's real fusion rule and the
   merged grouping library; about 1,400 model calls for the tree if limits or
   prompt change (free if they do not: every summary is cached by node hash).
2. **`guide` at the deadline**: on `F` and `G` from the latency experiment.
3. **A usable answer component**: on sources the reader does not know, or a
   judged answer scorer; the pattern check cannot rank long context fairly.
4. **Confirmation whole-document cases**: nine more to author before sealing
   is meaningful for that class.
5. **Larger case sets**: the kill rule's thresholds against the case count.
