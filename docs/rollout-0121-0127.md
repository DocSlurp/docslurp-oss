# Rollout: migrations 0121-0127 (single release)

0121-0124 and 0126 are additive and change only the catalog. 0125 and 0127 are one-way and ship in this same release, with no
later contract step: DocSlurp is pre-release, the organization is the only tenant scope, and rows that cannot be given exactly
one organization are deleted now (owner decision, 2026-11-04). **Rollback means restoring the database snapshot taken right
before migrating** (below); there is no down migration, and the previous release does not run correctly on the new schema for
long (see [Mixed-version window](#mixed-version-window)).

| Migration | Change | Lock | Needs a follow-up |
| --- | --- | --- | --- |
| 0121 | Defines `docslurp_fold_text()` only | none on tables | Build the folded index (below) |
| 0122 | `documents.file_facts jsonb` | lock prelude (below); metadata only | no |
| 0123 | `upload_session_files.request_index`, `client_id` | lock prelude; metadata only | no |
| 0124 | `docslurp_workspace_access()` | none | no |
| 0125 | `webhooks.org_id NOT NULL` (no workspace scope) and `api_keys.org_id NOT NULL`; rows without exactly one organization deleted | lock prelude; `SET NOT NULL` scans `webhooks` and `api_keys` (small tables) | no |
| 0126 | `documents.billing_pages`, `billing_pages_method`, `page_count_source` | lock prelude; metadata only: plain `ADD COLUMN`, a constant `NOT NULL DEFAULT` (stored once in the catalog, no rewrite), CHECKs added `NOT VALID` | optional `VALIDATE CONSTRAINT` later |
| 0127 | One organization per user: extra memberships removed (backed up), owners promoted, `org_memberships_one_org_per_user` unique index | lock prelude; reads only the organizations of users with several memberships | no |

## Locks

The migrator applies every pending migration in **one transaction**, so the locks of 0122-0130 add up and are all held until it
commits. Every lock-taking migration of the release starts with the same **lock prelude**, so whichever runs first takes all of
the release's strong locks, in one canonical order, before changing anything (later ones re-take locks already held, a no-op):

1. `documents`, `upload_session_files`: ACCESS EXCLUSIVE, `lock_timeout` 10 s;
2. `organizations`, `org_memberships`: SHARE ROW EXCLUSIVE, 10 s;
3. `api_keys`: ACCESS EXCLUSIVE, 3 s (every API request reads it);
4. `webhooks`: ACCESS EXCLUSIVE, 10 s.

The order follows the application's own transactions, as 0063 does: the worker's terminal checkpoint updates `documents` and
runs, then reads `webhooks`, so `documents` comes before `webhooks`; organization changes (offboarding, membership changes) touch
the organization first, then memberships, keys, grants and webhooks. Taken one migration at a time, these locks used to be
acquired in a scattered order (`documents` in 0122, `organizations` in 0125, `org_memberships` last in 0127), and a transaction
holding a later table while waiting for an earlier one could deadlock with the migrator.

What the prelude does **not** guarantee: no fixed order can rule out a deadlock with a transaction that takes two of these tables
the other way round. Postgres detects a deadlock after `deadlock_timeout` (1 s) and aborts one side. If it aborts the migrator,
the whole transaction rolls back, nothing is half-applied, and the migration is re-run. `lock_timeout` likewise fails the
migration instead of queueing every reader of a hot table behind a long transaction.

While the migration runs, every reader of `documents` and `api_keys` waits: API requests and worker stage updates stall for its
duration. Nothing scans or rewrites `documents` under that lock (0122 and 0126 change the catalog only), so expect seconds. The
pre-deploy report gives `documents` rows and size and lists the transactions that would make a lock wait time out.

## Deploy order

1. **Pre-deploy check, from the new image.** The previous image does not contain the script. Start an ephemeral machine from the
   new app image (for Fly: `fly machine run <new image> --rm --app <app> -- node /app/core/server/db/predeploy-check.mjs --strict`;
   locally: `DATABASE_URL=<direct url> node server/db/predeploy-check.mjs --strict`). It is read-only (one `READ ONLY`
   transaction). Fix every `BLOCKER`; read every `WARN`. It reports:
   - pending migrations and transactions older than 30 s that would make a migration lock wait fail;
   - `documents` rows and size; `document_chunks` rows and size and the folded index's state and build budget;
   - how many `api_keys` and `webhooks` 0125 homes and how many it DELETES;
   - **every user 0127 affects**, from the migration's own plan SQL (read from `0127_one_org_per_user.sql`, so the report and the
     migration cannot drift): email (id when redacted), the organization kept, each organization removed (reason, role, whether it is funded, live
     keys and MCP grants to be revoked, workspaces handed over or deleted), owners promoted, and organizations left with no member;
   - stored pipelines whose `piiPolicy.patterns` the new build rejects (the old build accepted any string and scanned for nothing);
   - stored `documentExtraction` configs naming an extractor id this build does not know (built-in ids plus the
     `DOCSLURP_EXTRACTOR_ID_ALIASES` keys; run the check with the same value the API and worker will have);
   - completed stage states with no artifact, and the runs in flight by routing pin.

   **A removal from a funded organization** (a paid balance or auto top-up) **or any promotion to owner** (a plain member
   promoted is called out) is a `BLOCKER`
   until an owner has reviewed that exact list and re-runs the check with the `--ack-0127=<hash>` it prints. The hash covers the
   list; if the data changes, so does the hash. 0127 enforces this itself: it computes the same hash and aborts (nothing applied)
   unless the migrator runs with `DOCSLURP_ACK_0127=<hash>` (`server/db/migrate.mjs` passes it to the session as
   `docslurp.ack_0127`). A missing, stale or malformed value fails the migration with a message naming the counts; re-run the check.

   0127 never leaves a live organization with members but no owner. A team organization in that state (its last owner
   removed, or it had none) has its longest-standing admin, else member, promoted, and every promotion is in the
   acknowledgement. A personal organization in that state (its owner leaves while a guest stays) is never handed to another
   user: the report says `0127 WILL ABORT` and names it, the migration refuses to run, and an operator resolves it first
   (restore the owner, or remove or move the other members).

   Output is redacted (user and organization ids only, no emails or organization names) with `--redact`, which CI and any
   logged run must pass, and whenever stdout is not a terminal. The owner reviews the full list from an interactive terminal
   (`--no-redact` forces it).

   0127 deletes a personal organization only when it is truly empty: no member but its owner, no documents, runs, chats, upload
   in flight, media job, connector, share or workspace invite, no live key, MCP grant or webhook, no Stripe customer, and never
   funded. Its leftover empty workspaces are deleted with it (`workspaces.org_id` has no foreign key) and both are copied to
   `organizations_removed_backup`. Anything less is kept with its data.
2. **Snapshot.** Take a Neon snapshot (or branch) of the production database right before migrating, after the check passes.
   This snapshot is the rollback.
3. **Migrate, as a standalone step**: the app repository's `scripts/fly-migrate.mjs` (a one-off machine from the new image running
   `server/db/migrate.mjs`). Never through Fly's `release_command` for this release: it would migrate as part of `fly deploy`,
   without the check and the snapshot in front of it. Expect seconds. On a `55P03` (lock timeout) or `40P01` (deadlock), nothing
   was applied: wait for `pg_stat_activity` to quiet down and re-run.
4. **Build the folded index**, once, while traffic flows: `node server/db/folded-search-index.mjs` (`--status` to look,
   `--dry-run` to see what it would do). It runs `CREATE INDEX CONCURRENTLY` on `to_tsvector('simple', docslurp_fold_text(text))`,
   which blocks neither reads nor writes, and must run after the migration: `CONCURRENTLY` cannot run inside the migrator's
   transaction. It is idempotent, keeps a build advisory lock, and drops and rebuilds an INVALID leftover.
   - Locks: each attempt first probes the table's SHARE UPDATE EXCLUSIVE lock under `FOLDED_INDEX_LOCK_TIMEOUT_MS` (default 5 s)
     and retries later when DDL or a manual VACUUM holds it (`FOLDED_INDEX_ATTEMPTS`, `FOLDED_INDEX_RETRY_DELAY_MS`). The build then
     runs with `lock_timeout = 0`, because `CONCURRENTLY` waits for every older transaction and a short timeout there would fail a
     long build at its end.
   - Memory: `FOLDED_INDEX_MAINTENANCE_WORK_MEM` (default `128MB`) is the build's sort memory on the database server. Size it to the
     compute: up to about a quarter of its RAM while nothing else heavy runs (a 0.25 CU Neon compute has 1 GB; 1 CU has 4 GB).
     More memory makes the build faster, and too much risks the database's memory.
   - Measured on a throwaway postgres:17: 200k rows of ~2 KB text took 159 s while inserts continued. Until the index exists,
     keyword search still works: the folded leg (non-ASCII queries and English-empty fallbacks) scans the workspace's chunks under
     `SEARCH_FOLDED_UNINDEXED_TIMEOUT_MS` (default 2000 ms) and contributes nothing when cut off.
5. **Workers**, then **the app**.
6. **Canary**: sign in, upload a small PDF and a DOCX, search with a non-ASCII term, ask a chat question, create and delete an API
   key, and send a test webhook from an organization that has one.
7. **Watch SigNoz** at the points below for the first hour.

## What is not rollback-safe

Restoring the snapshot is the only rollback. Rolling back only the code onto the new schema is not supported, and these changes
cannot be undone without the snapshot:

- **0125** deleted webhooks (with their delivery log) and API keys that could not be given exactly one organization. No copy is kept.
- **0127** removed memberships (a copy is in `org_memberships_removed_backup`), revoked those users' API keys and MCP grants in
  the organizations they left, deleted their direct workspace shares there, reassigned their workspaces, promoted owners, and
  **deleted empty personal organizations**. Reinstating a membership from the backup does not un-revoke keys or restore shares.
- Anything written after the migration (new documents, runs, keys, billing events) is lost when the snapshot is restored; restore
  only on a failed rollout, before real traffic has written much.
- Old code on the new schema: an N-1 app omits `webhooks.org_id` and `api_keys.org_id` on insert (500s) and does not know the
  one-organization index.

## What 0125 and 0127 delete

**0125, webhooks.** A webhook used to belong to the user who created it. It now belongs to one organization (no per-workspace
scope) and delivers that organization's run events while its creator is still an owner or admin there. A legacy webhook is
moved to an organization only when its creator belongs to exactly one live organization and administers it; every other one is
deleted with its delivery log. Recreate deleted webhooks per organization after the deploy (the pre-deploy report counts them).

**0125, API keys.** `validateApiKey` never served a key without an organization. Such a key is moved, still revoked, to its
owner's organization when the owner has exactly one, and deleted otherwise (revoked or not).

**0127, memberships.** A user belongs to one organization while `DOCSLURP_MAX_ORGS_PER_USER` is 1
([api-sdk.md](api-sdk.md#one-organization-per-user)). In order:

1. Every membership in a tombstoned organization is removed, whatever else the user belongs to.
2. A user's own personal organization is deleted when it is empty (no documents, runs, unrevoked API keys or webhooks, never
   paid) and the user keeps another live membership. A revoked key is not data.
3. Of the rest one membership is kept: a team organization before a personal one, then the organization with the most recent run
   or document, then the stronger role (owner, admin, member), then the longest-standing membership. The others are removed as a
   member removal: keys and MCP grants there revoked, direct workspace shares deleted.
4. No live team organization is left without an owner while it has members: when its last owner is removed, its
   longest-standing admin, else its longest-standing member, becomes owner (`audit_log` action
   `organization.member.promoted_to_owner`). Workspaces the removed user owned pass to the organization's longest-standing owner,
   the promoted one included.

Removed memberships are copied to `org_memberships_removed_backup` (the worker role cannot read it). An organization left with no
member keeps its data; the pre-deploy report names it so an operator can reinstate a membership from the backup. A user whose only
membership was in a tombstoned organization is left with none and gets a personal organization at their next sign-in.

The API logs `[org-limit] DOCSLURP_MAX_ORGS_PER_USER=<n> has no effect` at startup when the variable is above 1 while the unique
index exists: the index keeps refusing a second membership until a migration drops it.

## Mixed-version window

For the minutes between the migration and the last old machine, release N-1 runs against the new schema:

- An N-1 app creating a webhook omits `org_id` and gets a 500; retry after the app rolls.
- N-1 workers check webhook subscriptions by `webhooks.user_id`. The worker role keeps its `SELECT` grant on `user_id` for this
  release (`server/db/roles.mjs`), so their terminal-checkpoint outbox insert keeps working; a later release drops that column
  grant once no N-1 worker can be running.
- An N-1 app accepting an invite into a second organization hits the unique index and answers 409 (`organization_conflict`).

Evidence routing pins `v3` in `run:vision-routing-version`. The previous release pinned `v2` for its keyword canary, so reusing
`v2` would let an old worker route a new run with the old rules. An old worker does not know `v3` and routes as `v1` with a
warning; this release reads any pin other than `v3` (including `v2`) as `v1`.

## What to watch in SigNoz

Before the migration (baseline), during it, and at least every five minutes for the first hour of workers:

- **Migration**: `[migrate] complete in ...ms` from the migrate machine. A `55P03` (lock timeout) or `40P01` (deadlock) failure
  rolled everything back; re-run once `pg_stat_activity` is quiet. API latency and worker stage latency should spike only for the
  migration's seconds.
- **Index build**: `[folded-index] built ... in ...ms`, `[folded-index] attempt N failed` (a busy probe, retried);
  `pg_stat_progress_create_index` while it runs. Inserts into `document_chunks` (worker `embed`/`index` stage latency) should not move.
- **Keyword search**: `foldedUnindexedTimeout` in search timings and `[search] folded keyword leg cut off` log lines mean the index is
  not built yet; they stop once it is valid. Compare lexical branch latency and `lexicalTimeout` before and after.
- **Routing**: `[classify-route] ... routing=v3 pages= measured= read= reasons={...} blank= repeatedImagePages= textLayer={...} ocrChecked=`
  per document, with the same fields in the `classify-route` stage stats (`intakePages` vs `measuredPages`, `pagesRead`,
  `pagesReadByReason`, `blankPages`, `repeatedImagePages`, `textLayerVerdicts`, `textLayerOcrChecked`, `textLayerOcrDisagrees`), and
  `selectedPageCount` / `failedPageCount` / `documentPages` in `vision-extract`. A large gap between `measuredPages` and `intakePages`, or
  `[vision-routing] ... routing as v1` warnings after the old workers drain, needs a look.
- **Fail-closed readers**: `ArtifactReadError` (retried by the stage) is the signal for a recorded artifact that cannot be read; a rise
  after the deploy is the readers refusing to answer from the raw source.
- **Webhooks**: `webhook_outbox` rows dispatched per run, and no `permission denied for table webhooks` from N-1 workers. `last_error`
  values starting `Skipped:` name why an event was not delivered (no run, workspace/run mismatch, notifications off, creator no longer
  an owner or admin). A team whose webhook stopped firing is one the pre-deploy report counted as deleted.
- **Memberships**: `user_already_in_org` 409s on invite accept and organization create are the policy working; a spike right after
  the deploy is users whose extra memberships 0127 removed. `[org-limit]` at API startup means the limit variable and the index disagree.
