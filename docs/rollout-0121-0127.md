# Rollout: migrations 0121-0127 (single release)

The Fly release path migrates first, then rolls workers, then the app (`scripts/fly-migrate.mjs` in the app repo;
[releases.md](releases.md)). 0121-0124 and 0126 are additive with short locks. 0125 and 0127 are one-way and ship in this same
release, with no later contract step: DocSlurp is pre-release, the organization is the only tenant scope, and rows that cannot
be given exactly one organization are deleted now (owner decision, 2026-11-04). A rollback to the previous release is not
supported once 0125 has run; restore from a backup instead.

| Migration | Change | Lock taken | Needs a follow-up |
| --- | --- | --- | --- |
| 0121 | Defines `docslurp_fold_text()` only | none on tables | Build the folded index (below) |
| 0122 | `documents.file_facts jsonb` | `documents` ACCESS EXCLUSIVE, metadata only, `lock_timeout` 10 s | no |
| 0123 | `upload_session_files.request_index`, `client_id` | `upload_session_files` ACCESS EXCLUSIVE, metadata only, `lock_timeout` 10 s | no |
| 0124 | Access predicate (historical SQL name `docslurp_workspace_access`; renamed by 0128) | none | no |
| 0125 | `webhooks.org_id NOT NULL` (no project scope) and `api_keys.org_id NOT NULL`; rows without exactly one organization deleted | `organizations` SHARE ROW EXCLUSIVE, then `webhooks` ACCESS EXCLUSIVE (10 s); `api_keys` (3 s) | no |
| 0126 | Document billing pages | see the migration | no |
| 0127 | One organization per user: extra memberships removed (backed up), `org_memberships_one_org_per_user` unique index | `organizations`, `org_memberships` SHARE ROW EXCLUSIVE (10 s) | no |

The coordinated terminology cutover adds **0128_projects** after this chain. It renames live workspace tables, columns and routines to projects; historical migrations above remain unchanged. Drain old producers and replace server, worker, app and clients together. The predeploy report supports both schema generations and refuses an ambiguous mixed schema.

A migration that cannot get its lock within `lock_timeout` fails the release step instead of queueing every reader of
a hot table behind a long transaction. Re-run the release after the blocking transaction ends. Lock order follows
0063: `organizations` before `webhooks`, the order a worker transaction takes them, so the two cannot deadlock.

## Order

1. **Before**: `DATABASE_URL=<direct url> node server/db/predeploy-check.mjs --strict` (in the app image:
   `fly ssh console -C "node /app/core/server/db/predeploy-check.mjs --strict"`). It is read-only. Fix every
   `BLOCKER`; read every `WARN`. It reports `document_chunks` rows and size, how many `api_keys` and `webhooks` 0125 homes
   and how many it DELETES, how many memberships 0127 removes (by rule), stored pipelines whose `piiPolicy.patterns` the new build rejects
   (the old build accepted any string and scanned for nothing), completed stage states with no artifact, runs in flight by
   routing pin, and transactions older than 30 s that would make a migration lock wait fail.
2. **Migrate** (`scripts/fly-migrate.mjs`). Takes seconds. Nothing rewrites a table.
3. **Build the folded index**, once, while traffic flows: `node server/db/folded-search-index.mjs`
   (`--status` to look, `--dry-run` to see what it would do). It runs `CREATE INDEX CONCURRENTLY` on
   `to_tsvector('simple', docslurp_fold_text(text))`, which blocks neither reads nor writes. It is idempotent, drops and rebuilds
   an INVALID leftover, keeps a build advisory lock, and retries on `lock_timeout`
   (`FOLDED_INDEX_LOCK_TIMEOUT_MS`, `FOLDED_INDEX_ATTEMPTS`, `FOLDED_INDEX_MAINTENANCE_WORK_MEM`). Measured on a throwaway
   postgres:17: 200k rows of ~2 KB text took 159 s while inserts into the table continued (worst insert 250 ms including
   `docker exec`), where the stored generated column it replaced held ACCESS EXCLUSIVE for 221 s plus 81 s of index build.
   Until the index exists keyword search still works: the folded leg (non-ASCII queries and English-empty fallbacks) scans the
   project's chunks under `SEARCH_FOLDED_UNINDEXED_TIMEOUT_MS` (default 2000 ms) and contributes nothing when cut off;
   the English leg is unaffected. The query is cached for 5 minutes once the index is valid and 30 s while it is missing.
4. **Workers**, then the **app**, as usual. Watch SigNoz (below).

Order matters in one place: the index build is after the migration, never inside it. `CREATE INDEX CONCURRENTLY` cannot run
in the migrator's transaction, and the migrator applies every pending migration in one.

## What 0125 and 0127 delete

**0125, webhooks.** A webhook used to belong to the user who created it. It now belongs to one organization (no per-project
scope) and delivers that organization's run events while its creator is still an owner or admin there. A legacy webhook is
moved to an organization only when its creator belongs to exactly one live organization and administers it; every other one is
deleted with its delivery log. There is no backup: it would only keep signing secrets nobody can use. Recreate deleted webhooks
per organization after the deploy (the pre-deploy report counts them).

**0125, API keys.** `validateApiKey` never served a key without an organization. Such a key is moved, still revoked, to its
owner's organization when the owner has exactly one, and deleted otherwise (revoked or not). Every insert path sets `org_id`:
`createApiKey`, `rotateApiKey` (`api-keys.ts`) and `createGrant` (`mcp-oauth.ts`).

**0127, memberships.** A user belongs to one organization while `DOCSLURP_MAX_ORGS_PER_USER` is 1
([api-sdk.md](api-sdk.md#one-organization-per-user)). For a user with several memberships, in order: memberships in tombstoned
organizations go; their own personal organization goes if it is empty (no documents, runs, API keys or webhooks, never paid);
of the rest one is kept (owner/admin before member, then the organization with the most recent run or document, then the newest
membership). Removed memberships are copied to `org_memberships_removed_backup` (the worker role cannot read it) and handled as a
member removal: keys and MCP grants there are revoked, direct project shares deleted, projects they owned pass to the
longest-standing owner. Organizations and their data are kept, even one left without members.

## Mixed-version window

For the minutes between the migration and the last old machine, release N-1 runs against the new schema:

- An N-1 app creating a webhook omits `org_id` and gets a 500; retry after the app rolls.
- N-1 workers check subscriptions by `webhooks.user_id`, which the worker role can no longer read once roles are reconciled; their
  outbox insert then fails and the run's terminal checkpoint is retried by the new workers. Keep the window short.
- An N-1 app accepting an invite into a second organization hits the unique index and answers 409 (`organization_conflict`).

Evidence routing pins `v3` in `run:vision-routing-version`. The previous release pinned `v2` for its keyword canary, so reusing
`v2` would let an old worker route a new run with the old rules. An old worker does not know `v3` and routes as `v1` with a
warning; this release reads any pin other than `v3` (including `v2`) as `v1`.

## What to watch in SigNoz

During the migration and the first hour of workers:

- **Migration**: `[migrate] complete in ...ms` from the release machine; a `55P03` / `lock timeout` failure means a long transaction
  blocked it, so retry once `pg_stat_activity` is quiet (the pre-deploy report lists them).
- **Index build**: `[folded-index] built ... in ...ms`; `pg_stat_progress_create_index` while it runs. Inserts into `document_chunks`
  (worker `embed`/`index` stage latency) should not move.
- **Keyword search**: `foldedUnindexedTimeout` in search timings and `[search] folded keyword leg cut off` log lines mean the index is
  not built yet; they stop once it is valid. Compare lexical branch latency and `lexicalTimeout` before and after.
- **Routing**: `[classify-route] ... routing=v3 pages= measured= read= reasons={...} blank= repeatedImagePages= textLayer={...} ocrChecked=`
  per document, with the same fields in the `classify-route` stage stats (`intakePages` vs `measuredPages`, `pagesRead`,
  `pagesReadByReason`, `blankPages`, `repeatedImagePages`, `textLayerVerdicts`, `textLayerOcrChecked`, `textLayerOcrDisagrees`), and
  `selectedPageCount` / `failedPageCount` / `documentPages` in `vision-extract`. A large gap between `measuredPages` and `intakePages`, or
  `[vision-routing] ... routing as v1` warnings after the old workers drain, needs a look.
- **Fail-closed readers**: `ArtifactReadError` (retried by the stage) is the signal for a recorded artifact that cannot be read; a rise
  after the deploy is the readers refusing to answer from the raw source.
- **Webhooks**: `webhook_outbox` rows dispatched per run. `last_error` values starting `Skipped:` name why an event was not delivered
  (no run, project/run mismatch, notifications off, creator no longer an owner or admin). A team whose webhook stopped firing is
  one the pre-deploy report counted as deleted.
- **Memberships**: `user_already_in_org` 409s on invite accept and organization create are the policy working; a spike right after
  the deploy is users whose extra memberships 0127 removed.
